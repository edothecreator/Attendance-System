1. PROJECT OVERVIEW
================================================================================

AttendAI is an automated attendance system that uses facial recognition to
identify students in class videos. Professors record their class via the
browser camera, and the AI identifies which students are present by comparing
detected faces against enrolled student embeddings. Students not detected are
automatically marked absent.

The system includes role-based access (admin, professor, student), automated
email alerts, QR code fallback with geolocation verification, a student
self-service portal with reclamation workflow, analytics dashboards, and
official PDF report generation.

Target Institution: FST Marrakech (Faculté des Sciences et Techniques)
Class Structure: 1 class, 7 modules, 14 weeks per module

4. DATABASE SCHEMA
================================================================================

TABLE: users
  - id              UUID (PK)
  - username        VARCHAR(100) UNIQUE
  - password_hash   VARCHAR(255)
  - name            VARCHAR(255)
  - role            VARCHAR(50)        -- "admin" or "professor"
  - profile_image   TEXT (nullable)
  - module_id       UUID (FK → modules.id, nullable)
  - created_at      TIMESTAMP

TABLE: students
  - id              UUID (PK)
  - student_id      VARCHAR(50) UNIQUE  -- CNE/Apogée number
  - name            VARCHAR(255)
  - email           VARCHAR(255) (nullable)
  - profile_image   TEXT (nullable)     -- base64 encoded image
  - created_at      TIMESTAMP

TABLE: face_embeddings
  - id              UUID (PK)
  - student_ref     UUID (FK → students.id, CASCADE)
  - embedding       FLOAT[512]          -- 512-dimensional vector
  - created_at      TIMESTAMP
  NOTE: Multiple embeddings per student (one per enrollment photo)

TABLE: modules
  - id              UUID (PK)
  - name            VARCHAR(255)
  - code            VARCHAR(50) UNIQUE
  - total_weeks     INTEGER (default 14)
  - created_at      TIMESTAMP

TABLE: sessions
  - id              UUID (PK)
  - module_id       UUID (FK → modules.id, CASCADE)
  - week_number     INTEGER
  - session_date    TIMESTAMP
  - video_filename  VARCHAR(255)
  - status          VARCHAR(50)         -- pending/processing/completed/failed
  - created_at      TIMESTAMP

TABLE: attendance_records
  - id              UUID (PK)
  - session_id      UUID (FK → sessions.id, CASCADE)
  - student_ref     UUID (FK → students.id, CASCADE)
  - is_present      BOOLEAN
  - confidence      FLOAT (nullable)    -- AI confidence, 0.99=QR, -1=justified
  - detected_at_sec FLOAT (nullable)    -- timestamp in video
  - created_at      TIMESTAMP

TABLE: reclamations
  - id              UUID (PK)
  - student_ref     UUID (FK → students.id, CASCADE)
  - session_id      UUID (FK → sessions.id, CASCADE)
  - message         TEXT
  - attachment      TEXT (nullable)     -- base64 encoded file
  - status          VARCHAR(50)         -- pending/approved/declined
  - professor_response TEXT (nullable)
  - created_at      TIMESTAMP
  - resolved_at     TIMESTAMP (nullable)

7. AI PIPELINE
================================================================================

ENROLLMENT FLOW:
  1. Admin uploads 3-10 photos of a student
  2. Each photo validated (at least one face must exist)
  3. DeepFace extracts 512-d embedding from each photo (Facenet512)
  4. Fallback chain: MTCNN → OpenCV → SSD → skip (for detection)
  5. ALL individual embeddings stored (not averaged)
  6. First photo (or selected one) becomes profile picture

IDENTIFICATION FLOW (Video Processing):
  1. Professor records class via browser camera
  2. Video uploaded, background worker starts
  3. Frames extracted at 2 FPS
  4. Each frame preprocessed:
     - BGR → RGB conversion
     - Upscaling if < 640px
     - CLAHE brightness/contrast for dark frames
  5. MTCNN detects faces (min 50x50px)
  6. Each face embedded via Facenet512
  7. Cosine similarity matching against all stored embeddings
  8. Margin check: reject if best and second-best are too close (<0.05)
  9. Threshold: 0.55 cosine similarity
  10. Best confidence per student kept (deduplicated)
  11. Results broadcast via WebSocket in real-time
  12. All students marked: detected=present, not detected=absent
  13. Email alerts triggered for students hitting 2+ absences


8. QR CODE FALLBACK SYSTEM
================================================================================

Purpose: Allow students missed by AI to check in physically.

FLOW:
  1. Professor completes a session (video processed)
  2. Goes to Sessions → clicks "Generate QR"
  3. Browser captures professor's GPS location
  4. QR code generated with unique token (expires in 10 minutes)
  5. QR encodes a URL: https://[domain]/portal?token=[uuid]
  6. Professor displays QR to class (projector/phone)
  7. Student scans with phone camera → opens portal with token pre-filled
  8. Student logs in → taps "Check In"
  9. Student's GPS captured → verified within 50m of professor
  10. If within range → marked as present (confidence: 0.99 = "QR Code")

PROTECTIONS:
  - 10-minute expiry
  - Single-use per student
  - Geolocation verification (50m radius) when available
  - Student must be enrolled and authenticated
  - Falls back to time-only protection if GPS unavailable


9. RECLAMATION WORKFLOW
================================================================================

STUDENT SUBMITS:
  1. Student sees red (absent) week dot in their portal
  2. Taps it → modal opens
  3. Writes justification reason
  4. Optionally attaches medical certificate (image/PDF, max 5MB)
  5. Submits → status: "pending"
  6. Professor receives email notification
  7. In-app notification appears in professor's bell

PROFESSOR REVIEWS:
  1. Goes to Reclamations page (sidebar)
  2. Sees pending requests with student info, message, attachment
  3. Clicks "Review & Respond"
  4. Types optional response
  5. Clicks "Approve" or "Decline"

RESULT:
  - Approved: absence marked as "justified" (confidence = -1)
  - Declined: absence remains unjustified
  - Student receives email with decision + professor's response
  - Action logged in audit trail

14. BUSINESS RULES
================================================================================

Sequential Weeks:
  - Professors must take attendance in order (Week 1 → 2 → 3...)
  - Cannot skip to Week 3 without completing Weeks 1 and 2
  - CAN retake any previously completed week (overwrites old data)
  - Admin can bypass this restriction

Module Ownership:
  - Each professor is assigned to exactly one module
  - They can ONLY record videos for their assigned module
  - They can ONLY view sessions for their module
  - Admin has access to all modules

Attendance Logic:
  - Detected in video → is_present = True + confidence score
  - Not detected → is_present = False
  - QR check-in → is_present = True, confidence = 0.99
  - Justified (approved reclamation) → is_present = False, confidence = -1
  - Retaking a week deletes old session and all its attendance records

Email Triggers:
  - 2 absences in any module → first warning email to student
  - 3 absences in any module → critical warning email
  - Reclamation submitted → notification email to professor
  - Reclamation resolved → result email to student

Exclusion Threshold:
  - 3+ unjustified absences in a module = critical risk
  - Flagged on analytics dashboard


15. SECURITY NOTES
================================================================================

- Passwords hashed with bcrypt
- JWT tokens expire after 24 hours
- CORS restricted to frontend origin
- File uploads validated (type + size limits)
- SQL injection prevented via SQLAlchemy ORM
- Profile images stored as base64 in DB (no file system exposure)
- QR codes expire after 10 minutes, single-use, geo-verified
- Student portal isolated from admin routes
- Audit log tracks all significant actions

Production Recommendations:
- Change SECRET_KEY in auth.py to a random 64-char string
- Use proper HTTPS (not self-signed)
- Set stricter CORS origins
- Add rate limiting
- Store videos in cloud storage (S3) instead of local disk
- Move notifications/audit to database tables (currently in-memory)
- Add proper logging and monitoring
